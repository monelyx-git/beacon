# Beacon i18n: design

Supersedes the "multiple languages" non-goal in `2026-11-06-beacon-design.md`. Everything else in that document still applies (budgets, stack, English-only repo conventions).

## Intent

A site built with Beacon can publish the same docs in several languages. The first real case: Pier's docs site (`pier-by-monelyx/docs-site`) must ship in English (default) and Spanish. This is about the **content** of the generated site, not about translating Beacon's CLI messages.

Why: Pier's users read Spanish and English. Authors should add a language by adding a folder, not by learning a framework.

## Goals

- **Minimal for authors.** `content/` stays the default language, untouched. `content/es/*` mirrors it for Spanish. One new config field.
- **Zero cost when unused.** No `locales` in the config means identical output to today. A folder that happens to be called `es` is just a folder.
- **Static and light.** No server, no language detection script, no new dependency, no budget regression on sites that do not use it.
- **Good SEO.** `<html lang>`, `hreflang` alternates, per-language search.

## Non-goals

Translated URL slugs (the URL is the file path), per-language `title`/`logo`/OG image, right-to-left layouts, machine translation, redirecting visitors by browser language, a fallback that shows default-language content under another language's URL, more than one level of locale nesting (`content/es/mx/`), versioned docs.

## Anti-goals

- Authors needing a directory layout other than "mirror the tree in a language folder".
- A build that fails because a translation is missing. Missing translations are a warning, never an error.
- Chrome strings ("On this page", "Search") hardcoded in English with no way to localize them.

## Decisions (as agreed)

- **Layout.** Default language lives at `content/`. Other languages live at `content/<code>/`, mirroring the same relative paths: `content/es/install.md` is the translation of `content/install.md`.
- **URLs.** Default language has no prefix (`/install/`); others are prefixed (`/es/install/`).
- **Missing translation.** `/es/x/` does not exist if `content/es/x.md` does not. The language switcher on that page sends the visitor to the home of the other language. No English-under-Spanish fallback.

## Decisions (my calls, please review)

- **Config.** `"locales": ["en", "es"]`, array of lowercase codes (`en`, `es`, `pt-br`). The first is the default language. A single entry (`["es"]`) is valid and just sets `<html lang>` for a one-language site. Invalid, empty or duplicate codes are a config error. Absent means today's behavior with `lang="en"`.
- **Routing comes almost free.** `scanContent` already walks `content/` recursively, so `content/es/install.md` already gets slug `es/install`. The work is to group pages by locale, not to invent routes.
- **Reserved folder.** When `locales` is set, a folder in `content/` named like a non-default locale code is that language, not a section. A default-language page whose slug collides is already a slug-collision error.
- **Navigation.** `buildNav` runs once per locale on that locale's pages (locale prefix stripped from the tree, kept in the hrefs). Folder labels are still derived from folder names; translators set a translated label by adding an `index.md` in the folder. Known limitation, documented, not solved.
- **Counterpart lookup.** A page's translation is the page with the same relative path in the other locale. The switcher lists every configured locale, linking to the counterpart if it exists, else to that locale's home. If the locale has no home page it uses the existing root-redirect rule (first page of that locale's nav).
- **Root of each locale.** `/` and `/es/` each get a page or the existing redirect, computed per locale.
- **Head tags.** `<html lang>` from the page's locale. For pages that have at least one translation, emit `<link rel="alternate" hreflang>` for every available version plus `x-default` pointing at the default language. Sitemap lists all URLs; alternates in the sitemap are not part of this change.
- **Chrome strings.** One small plain object per locale (English and Spanish shipped) in `src/site/lib/`, covering every user-visible string in the layout and components (builder to inventory them: sidebar, TOC heading, search UI, theme toggle, 404, copy button, breadcrumb, language switcher). Locales without a dictionary fall back to English strings. No i18n library.
- **Search.** Pagefind indexes per `<html lang>` and searches the current page's language by default. The builder verifies this against the custom `SearchDialog`; if the API needs an explicit filter, pass the current locale.
- **Links.** Relative `.md` links already resolve by file path, so a link inside `content/es/` to a sibling resolves to the `es` page. A link from a Spanish page to a file that only exists in the default language resolves to that English page; that is accepted, it beats a dead link.
- **Missing-translation report.** The build logs, once, the list of default-language pages with no counterpart in each other locale. Warning only.
- **Dev.** `beacon dev` serves every language; the existing watcher already covers `content/**`. Config changes still need a restart, as today.
- **404 page.** Stays a single page in the default language in this change.
- **Spec and README.** The README gains a short "Languages" section. Pier's docs-site gets `locales` and a `content/es/` only after this feature ships, in Pier's repo, not here.

## Calls made after the builder check (my calls, please review)

- **Search is spiked first.** Pagefind splits its index by `<html lang>` in a single run, so no extra invocation is expected. The first task is a short spike proving that against `SearchDialog`. Fallback if it fails: one index, with a `locale` filter attribute passed by the dialog. No separate indexes per language.
- **Reserved folders.** Every configured code is reserved, the default included: `content/en/` with `en` as default is a config error telling the author to move the files up one level. A folder named after a code that is not configured stays a plain section.
- **Nav order.** Each locale's nav is built only from that locale's own pages and their own `order` frontmatter. It does not follow the default tree. Translators who want the same order copy the `order` values.
- **Switcher visibility.** Hidden when `locales` has one entry. Every configured locale is listed otherwise. A configured locale with no pages is a build error, since it would be a dead link.
- **Absolute URLs.** `hreflang` and `x-default` use the existing required `site` field (base URL, including its path). No new config field.
- **Existing tests.** Markup may change as long as output is byte-identical when `locales` is unset, which is what the existing tests assert. They should not need edits; if one does, that is a regression to fix, not a test to loosen.
- **Counterparts match by file path only.** Frontmatter such as `order` or `title` never affects matching.

## Constraints

- Everything in English (code, UI copy, docs, commits). No new dependencies, so no ADR is expected; if the builder finds one is needed, stop and raise it.
- Budgets from the main design must hold; a site with `locales` unset is measured unchanged.
- Existing tests must pass untouched. New behavior gets its own fixture (`test/fixtures/i18n`) with `en` default and `es`, including a page with no translation.

## Left to the builder

Internal shape of the per-locale data in the virtual module; how pages and nav are keyed by locale; where the language switcher sits in the sidebar (next to the theme toggle is expected); exact wording of the Spanish strings; how the missing-translation report is formatted; test layout beyond the fixture above.

## Acceptance

Building the Pier docs-site with a `content/es/` containing a couple of translated pages produces `/` and `/es/` trees, each with its own sidebar, `lang`, search results and working switcher, and the untranslated pages are listed as warnings.
